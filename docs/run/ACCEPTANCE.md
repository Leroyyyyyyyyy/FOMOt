## 2. 验收口径

- **禁发送**：`notification_log` 里 `mode='telegram'` 的行数必须为 **0**。
- **不把缺失显示为零**：卡片上任何 `n/a` 都必须伴随覆盖率，且不得由别的量顶替。
- **不把部分结果显示为完整**：Top10 收益只有在覆盖齐全、窗口一致时才给合计。
- **任务终态**：每条到期任务要么 `completed`，要么带可解释的 `abandoned`/`degraded` 与 `last_error`。
- **关键数字可复算**：`docs/run/evidence/samples.json` 里带够复算 Top10 收益与人数的原始行。

## 3. 指标口径

`run_metrics` 表按 `phase` 分 `startup`（进程启动后前 120 秒）与 `steady`。
两段分开统计——重启后 RPC 压力大、队列深，混在一起会同时高估稳态、低估恢复期。

| 指标 | 含义 |
|---|---|
| `scan_tick_ms` | 一次候选扫描（`engine.tick()`）耗时 |
| `initial_latency_ms` | 初值快照完成时刻 − 首次触发时刻。配置目标 800ms |
| `recheck_lateness_ms` | 复核完成时刻 − **原定**到期时刻（不是相对上一次重试）|
| `age_chain_ms` / `age_fomo_ms` / `age_board_ms` | 各数据源的数据年龄，分别追溯 |
| `chain_lag_blocks` | 扫链游标落后链头多少块 |
| `recheck_attempts` / `recheck_retry` | 复核尝试次数 / 重试发生次数 |
| `unfinished_alerts` | 处于 `firing` 或 `pending_recheck` 的任务数 |
| `rss_mb` / `heap_mb` / `tracked_tokens` | 内存与持币缓存规模 |

## 4.5 实跑抓到的缺陷（已修，但**不在**主验收窗口内验证）

**现象**：12:33 起 `refreshLeaderboard` 每 5 分钟失败一次，
`page.goto: Target page, context or browser has been closed`，共 6 次。
共享页被关掉后没有任何地方重建它，`tokenStats` 也再没法导航，
于是所有候选币永远停在「待预热」，**12:33 之后再没有产生过任何触发**
（7 次触发全部集中在前 33 分钟）。而 `ready` 始终是 true，
`recoverAuth()` 只在 `!ready` 时才跑，所以系统不会自愈。

**没有说假话**：榜单数据龄超过 10 分钟后 `leaderboardAvailable` 转 false，
卡片显示 `n/a`、健康行转红。第四阶段要的「降级而不是拿旧数据冒充」是成立的。
但可用性上这是个硬伤：数据源一挂，告警就整体停摆。

**修复**（`src/fomo/scraper.ts`）：
1. 新增 `ensurePage()`，`refreshLeaderboard` / `tokenStats` / `recoverAuth` 三条路径导航前都先确保页面可用；
2. 新增 `markStaleIfNeeded()`：关键业务接口超过 10 分钟没成功就主动把 `ready` 置 false、
   健康位记 `stale`，让 Engine 走 `!fomo.ready` 分支降级为纯链上模式继续告警；
3. 后台循环不再只看 `ready`，每轮先判 staleness 再决定是否 `recoverAuth()`。

回归测试见 `tests/fomo-health.test.ts`（5 项）。

**这个修复是在主验收窗口结束之后做的**，所以 §4.1/§4.2 的数字反映的是**修复前**的代码。
修复后的验证跑结果单列在 §5，不与主验收混算。

## 5.3 两个未解决的问题（实测量出来的，不是猜的）

### 复核延迟有长尾：一条晚了 288 秒

`0x88942e2016…`（RSO）21:08:24 触发、原定 21:13:25 到期、实际 21:18:12 完成，
**晚 288 秒，且重试次数为 0**。不是重启造成的（整条生命周期都在验证跑窗口内），
也没有数据丢失——最终状态是 `completed` / `complete`。

8 条复核里 P50 只有 5.3 秒，所以这是长尾而非普遍现象。
**最可能的成因**是持币调度器只给后台任务一个槽：`recheck` 在**排队顺序**上优先于 `prewarm`，
但一旦某个 `prewarm` 已经开跑（老币要从部署区块全量扫，可能好几分钟），
`recheck` 就得等它跑完。**这只是推断，日志不足以证实**——要坐实需要给调度器加
「排队等待时长」和「任务耗时」两个指标。在那之前不宜直接改并发参数。

按验收底线这条是**通过**的（到期任务完成了，状态可解释），但它是 0.8 秒性能目标之外
另一个真实的时延问题，记在这里而不是掩盖。

### 内存偏高且在长跑中增长

主验收稳态 RSS P50 518MB / 最大 799MB；验证跑 P50 **857MB** / 最大 **906MB**。
持币缓存只有 9~13 个代币，`sweepHolders` 在正常工作，所以主要占用应该在 Playwright 侧。
连跑几周的目标下这需要盯，本轮**未解决**。

## 9.1 为什么改成默认开启，以及改之前踩的坑

`platformPnl24h` 原本在 `enrich()` 里无条件调用，而 `enrich()` 在**初值**路径上。
第一次实跑就暴露了代价：

| 取数位置 | 初值延迟（实测）|
|---|---|
| 初值路径（原实现）| **70,966 ms / 49,127 ms** |
| 只在复核（现行）| **3,210 ms** |

Top10 十个人各要逛一次档案页，约 71 秒——`+0.8s` 的预算根本放不下。

改法有原图背书：原版截图那行标的是「Top10持币账户（**+5m1s**）」，
`+5m1s` 是复核阶段的偏移，说明**原版同样在复核阶段算这个数**。
现行实现加了 `priority === 'recheck'` 条件，初值卡先显示 `n/a`，五分钟后原地改写补上。
回归测试：`tests/recheck.test.ts`「全平台 24H 收益只在复核阶段取」。

## 9.4 填充率与四个 `n/a` 的成因

15 张复核卡片里 **11 张拿到真实数值**（含 3 个负数：−$6.67K / −$26.43K / −$52.36），4 张 `n/a`：

| 币 | 账户识别 | `n/a` 成因 |
|---|---|---|
| PILL / NOTHING / BODKIN | **0/0** | 复核时该币 FOMO 侧一个持币人都没有，Top10 是空集；「该币累计收益」同样是 `n/a（0/0）`，两个字段一致 |
| LYMBIC | 10/10 | 十人只取到 **9** 个序列 → `n/a（9/10）`。**设计意图**：差一个就不给合计 |

LYMBIC 最能说明两个字段是**各自独立**判断覆盖率的：
该币累计收益 `+$3.34K · 盈利 10 人`（齐全，照给），全平台 `n/a（9/10）`（不齐，不给）。
