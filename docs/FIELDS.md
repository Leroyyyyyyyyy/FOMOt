> 结论分三类：**已证实**（有可复现的观测）、**暂定口径**（有证据但不足以证明与原版一致）、
> **待确认**（没有证据，一律降级为 `n/a`）。
> 所有观测都来自用户已有登录态的浏览器；样本已脱敏，凭据从未进入日志或文件。

## 2. 三个关键证明

### 2.1 `/hodlers/top.pnl` 不是「全平台 24H 收益」

同一用户、几乎同一时刻，两个字段发散，且可以**反向**。
下表取自基线备份 `data/backups/fomot-20260905-190501.db`，
两侧采集时间差已精确到毫秒（`fomo_token_holders.updated_ts − fomo_leaderboard.updated_ts`）：

| 用户 | 代币 | `/hodlers/top.pnl` | 榜单 `pnl24h` | 两侧采集时间差 |
|---|---|---|---|---|
| Binkieee | 0x2f21… | **−6,158.67** | **+552,794.61** | −9,161 ms |
| looc | 0x2f21… | −5,147.92 | +197,973.31 | −9,161 ms |
| memeunc | 0x2f21… | +3,751.52 | +65,625.74 | −9,161 ms |
| ogle | 0x7dbf… | **−723.50** | **+658,581.21** | −13,501 ms |
| Avast | 0x7dbf… | +58,422.50 | +1,088,522.80 | −13,501 ms |
| Rowdy | 0x7dbf… | −5,137.98 | +81,419.49 | −13,501 ms |

9~14 秒的采集间隔解释不了「−6,158 对 +552,794」这种量级和符号的差异。

同一用户在不同代币上的 `pnl` 也不同（Unipcs 五个代币：+7,672,640 / −21,274 / −3,020 / −30,171 / −0.05），
所以它是 **per (user, token)**，不可能是用户级别的平台总收益。

复算：50/50 个持有人满足 `pnl == realizedPnl + unrealizedPnl`（误差 < 0.02）。

**因此：把 Top10 的 `/hodlers/top.pnl` 求和后标成「全平台24H PnL」是错误标签。已停止。**

**影响面**（基线备份 `fomot-20260905-190501.db`，55 个代币的 `/hodlers/top` 快照）：

| 项 | 值 |
|---|---|
| 有 Top10 快照的代币 | 55 |
| 旧代码会**印出数字**的（十人齐全且收益齐全）| **51** |
| 其中印出**负数**的 | 25 |
| 数字范围 | **−$431,865.17 ~ +$29,573,679.70** |

也就是说这不是个别情况：51 张卡片会把「该币全时段累计收益」标成「全平台24H PnL」。
量级最大的 PONS 会印出 `+$29.57M`——而该币当时市值远不足以支撑这个数，
本身就是这个标签不成立的旁证。

| 代币 | 旧卡片会印的「全平台24H PnL」 |
|---|---|
| PONS | +$29,573,679.70 |
| SHROOM | +$4,156,891.31 |
| MEME | +$1,881,924.34 |
| SLINK | **−$431,865.17** |


### 2.2 榜单 `pnl24h` 的确切定义

```
pnl24h = totalPnL(实时全时段累计)  −  aggregatedSnapshotById(userId, 最新整点 − 24h).pnl
```

单次同时刻观测复算（榜首 Unipcs）：
`19,352,384.503841717 − 16,053,435.471547 = 3,298,949.032295`，
实测 `pnl24h = 3,298,949.032294577`，**误差 1.4e-7**。

### 2.3 普通用户（未上榜 / 负收益）的全平台 24H 收益是可得的

`/v2/userTokens/aggregatedSnapshot?userId=…` 对**任意** userId 返回逐小时累计序列，
24H 收益 = `pnl[最新] − pnl[最新 − 24h]`。覆盖未上榜用户与负收益用户：

| 类型 | 用户 | 序列点数 | 24H delta | 榜单 pnl24h | 差 |
|---|---|---|---|---|---|
| 盈利榜 | Unipcs | 43 | +2,980,180.89 | 3,321,889.63 | −341,708.74 |
| 盈利榜 | ogle | 43 | +1,847,171.12 | 1,912,919.93 | −65,748.81 |
| 盈利榜 | Avast | 43 | +1,280,660.22 | 1,389,055.38 | −108,395.16 |
| 未上榜 | Fartman Sacks | 43 | **−98,090.26** | — | — |
| 未上榜 | BNBULL | 43 | **−4,206.78** | — | — |
| 未上榜 | Yaoza | 43 | +72,122.64 | — | — |

**残差解释（已定位，非缺陷）**：序列最新点是整点快照（11:00 UTC），榜单用的是**实时**累计值
（抓取于 11:18 UTC）。差额就是这 18 分钟的持仓浮动；Unipcs 权益约 $19M，1.8% 波动即约 $34 万。

> 所以有两个**不同**的量，必须分别命名：
> - `platform_pnl_24h_live`：仅盈利榜前 150 名可得（榜单直接给）。
> - `platform_pnl_24h_snapshot`：任意用户可得，窗口对齐到整点，比实时值滞后 ≤ 1 小时。

## 3.1 全平台 24H 收益的数据契约与窗口校验

实现见 [`src/engine/pnl.ts`](../src/engine/pnl.ts)，可追溯样例见
[`scripts/trace-pnl.ts`](../scripts/trace-pnl.ts)（`npx tsx scripts/trace-pnl.ts`）。

**一条收益记录必须携带这些字段，少一个都不足以证明「十个人算的是同一个 24 小时」：**

| 字段 | 含义 |
|---|---|
| `userId` / `value` | 谁、多少 |
| `source` | `aggregated_snapshot`（逐小时序列）或 `leaderboard_24h`（榜单） |
| `basis` | `snapshot`（两端对齐整点）或 `live`（右端是抓取时刻） |
| `windowStartTs` / `windowEndTs` | 窗口起止，毫秒 |
| `fetchedTs` | **实际获取时间**，与 `windowEndTs` 严格分开 |

> 「刚抓到」不等于「数据最新」。整点口径拿到手时，窗口右端可能已经是 59 分钟前——
> 这两件事用同一个字段表示，就是把滞后藏起来。

**取数与校验的硬规则：**

1. **一次聚合只定一个窗口。** `targetWindow(atMs)` 把时间向下取整到整点作为右端，
   往前 24 小时作为左端；十个人共用。中途跨整点也不重新挑「最新点」。
   整点快照有发布延迟，允许**整批**往前退最多一个整点（`anchorWindow`），退过之后不再变。
2. **起点必须精确命中。** 序列里找不到 `windowEndTs − 24h` 那个整点就返回
   `no_start_point`，绝不拿更早的点顶替——那会把 25 小时标成 24H。
3. **序列先排序去重查冲突。** 同一整点两个不同数值 → 整条序列作废（`conflicting_points`）；
   非有限数值剔除；剔掉的点若是端点，就是缺失，不是收益为 0。
4. **缓存键带口径与窗口**（`userId|basis|start-end`）。只按 userId 缓存十分钟，
   跨整点就会把上一小时的窗口混进这一小时的合计。
5. **聚合前四项一起校验**：成员完整性、数值有效性、口径一致性、起止时间一致性；
   再加一条窗口新鲜度（右端离现在 ≤ 2 小时）。任何一项不满足都返回
   `n/a` + 覆盖率 + **明确原因**，禁止部分求和冒充完整结果。

**实时榜单值的回退策略：不回退。**
榜单 `pnl24h` 的窗口右端是抓取时刻（`live`），与整点口径不是同一个 24 小时（§2.3 的残差就是这个差）。
它**不会**被补进 Top10 的合计——榜单值仍然用在「盈利榜持有人」那几行，那里是逐人展示、不参与求和。
本项目目前不做独立的实时聚合；要做的话必须另立一套时间一致性规则，不能和整点口径共用一行。

### 取数位置：完全在持币关键路径之外

取数代价是实测的：Top10 每人要单独逛一次档案页。历史实测：

| 取数位置 | 影响（实测）|
|---|---|
| 初值路径（最早的实现）| 初值 **70,966 / 49,127 ms** |
| 只在复核阶段同步取（上一版）| 复核延迟 P50 从 3.9s 变成 **56.6s**，卡片从 `+5m1s` 变成约 `+5m56s` |
| 完全解耦（现行）| 见 `docs/run/ACCEPTANCE.md` 本轮数据 |

现行做法：

- **预取**：复核到期前 120 秒，用初值那批已知成员按**到期时刻的整点窗口**预取；
- **到期**：重新确定实际 Top10，只复用**成员与窗口都匹配**的记录；新增成员没有记录 → 合计判缺失，
  绝不沿用旧 Top10 的总和；
- **未就绪**：持币复核照常完成并出卡，该行显示 `采集中…（N/M）`；
- **补入**：后续任务取到后**原地改写同一条卡片**，持币人数、采集时间与两个偏移一律不动。

任务状态落在 `alerts.pnl_state`：`off`（不需要补）/ `pending`（在补，带 `pnl_deadline_ts`）/
`ready`（已补入）/ `timeout`（到期没补上，卡片保持 `n/a`）。
同一告警不会重复启动同一个任务；已撤回或消息 id 变了的告警不会被迟到结果更新；
重启后 `pending` 且未过期的会接着补，过期的终结为 `timeout`。

- `FOMO_PLATFORM_PNL=0` 可关，关掉显示 `n/a`，不用该币收益冒充；
- 无论开关，**只有成员齐全、口径一致、窗口一致**才显示合计，否则 `n/a` + 覆盖率 + 原因。

### Top10 成员集合的可信度：`top10SetStatus`

「真的只有 3 个人」和「只采到 3 行」是两回事，不能单凭少返回几行就认定完整：

| 状态 | 判据 | 后果 |
|---|---|---|
| `ok` | 返回行数 ≥ `min(10, totalHolders)` | 正常统计，分母是实际集合大小 |
| `empty` | `totalHolders = 0` 且零行 | 两个收益字段都是 `n/a`，原因「该币 FOMO 侧无持币人」 |
| `incomplete` | 声称有人却行数不足 | 两个收益字段都是 `n/a`，原因「Top10 成员列表不完整」 |

## 3.2 卡片上的各来源时间

任务四要求这些时间分别可追溯、互不替代（实现见 `SourceTimes` / `StageResult`）：

| 时间 | 含义 |
|---|---|
| `triggerTs` / `originalDueTs` | 首次触发、原定复核时间（重试不覆盖后者）|
| `chainBlock` / `chainBlockTs` | 链上快照的区块号与区块时间 |
| `chainTakenTs` | 链上快照采集完成时间 |
| `fomoRespTs` | FOMO `/hodlers/top` 的响应时间 |
| **`holdersDoneTs`** | **持币采集阶段**（链上 + FOMO 持币）完成时刻 |
| `marketTakenTs` | 市值 / 成交量的取值时间 |
| `windowStartTs` / `windowEndTs` / `fetchedTs` | PnL 的窗口起止与获取完成时间 |
| `aggregatedTs` | 聚合完成时间 |
| `notification_log.ts` | **通知更新完成时间**（每次 send / edit / remove 各一行，带 `ca` + `trigger_ts`）|

前八项存在 `alerts.payload`（`StoredAlert.initial/recheck.times`）与
`holder_snapshots.payload` 里；通知更新完成时间存在 `notification_log`——
它本来就是每次通知出口操作各写一行，所以「卡片第几次改写、什么时候完成」是逐次可查的，
不需要在 payload 里再存一份会漂移的副本。`scripts/capture-evidence.ts` 把这两边一起导出。

**卡片上「持币初值（+…）／持币复核（+…）」的偏移 = `holdersDoneTs − triggerTs`**，
只由持币采集阶段决定。后面取 PnL 花 60 秒还是 6 分钟都不会把这个偏移撑大——
那是另一件事的耗时。`Top10持币账户（+…）` 用的是同一个偏移，表示**持仓集合**的时间；
收益窗口另行标注（`整点对齐口径（截至 …）`）。

允许的数据年龄与时间差（可用环境变量调）：
`FOMO_MAX_SOURCE_SKEW_MS`（默认 120s，链上与 FOMO 两侧采集时间差）、
`FOMO_MAX_SOURCE_AGE_MS`（默认 600s，单个来源的数据年龄）。
超限时卡片多出一行 `⚠️ 数据时点: …`，如实说明，不无条件当成同一时点。

## 3.5 钱包身份：`recipient` 是中转账户，不能直接当归属证据

`/v2/users/:userId/swaps` 每笔带一个 `recipient`。看起来像「这个用户的链上收款账户」，
但实测（cosby，100 笔）表明**不能这么用**：

| 观测 | 结果 |
|---|---|
| `provider` | 100/100 全是 `RELAY`（跨链中继）|
| 不同的 `recipient` 值 | 只有 **2 个**：`0xe6ab…c747`（EVM）与 `44ecVs…NEZC`（Solana）|
| 是否等于 `user.evmAddress`（`0xca3b0e…f80`）| **都不等于** |
| 交易哈希字段 | **没有** |
| 网络组合 | `4663←4663/1399811149` 47 笔、`4663←1399811149/4663` 20 笔、`8453←…` 10 笔、`56←…` 23 笔 |

`recipient` 随兑换**方向**在这两个值之间切换，也就是「目标链上的收款方」。

### 2026-09-06 判定结果：`recipient` **不能**用作本项目要的身份证据

按 §3.5 原定的判据跑了 `scripts/probe-recipient.ts ogle cosby`（证据：`docs/evidence/recipient-probe.json`）：

| 用户 | evmAddress | recipient（各 2 个：EVM + Solana）|
|---|---|---|
| ogle | `0x3a6962e0…1ebe9` | `0x39163eb2…e0628` / `7p2y6ux6…ydd6` |
| cosby | `0xca3b0e0e…3f80` | `0xe6ab6ee7…c747` / `44ecvsvh…nezc` |

**第一关过了**：`ogle ∩ cosby = 空`，两个用户的 recipient 集合互不相交
→ 不是中继的归集地址，像是用户专属的收款账户。

**第二关没过**：它不是持币的那个地址。三条独立观测：

| 检查 | ogle/cosby 的 recipient | 金额匹配出的交易账户 |
|---|---|---|
| `eth_getCode` | **纯 EOA** | **7702 委托**到 `0xe6cae83b…555b` |
| 8 小时内的 ERC20 Transfer | **收 0 / 发 0，0 个代币** | 收 0 / **发 22，8 个代币** |
| 出现在 `/hodlers/top.evmAddress` | **0 次** | — |

也就是说 recipient 是**另一条链**（Base 8453 / BSC 56 / Solana）上的收款地址，
在 Robinhood Chain 上根本没有代币活动。**拿它对不上 `/hodlers/top` 里的持仓。**

> 这一条的样本限制要说清楚：ogle 和 cosby 也可能只是最近 8 小时没在
> Robinhood Chain 上交易过，而那个有 22 笔的交易账户属于**另一个**用户，
> 所以这不是严格的对照实验。但 recipient 在整张 `fomo_token_holders` 表里
> **一次都没出现过**，这条不受样本限制影响。

### 更根本的一条：链上**没有**可用的密码学关联

`eth_getCode` 的观测（5/5 个候选交易账户）：

```
候选交易账户  0xd874259110c6…  0xef0100e6cae83b…  ← 7702，委托到 0xe6cae83bde06e4c305530e199d7217f42808555b
候选交易账户  0xf3a443d0a2c8…  0xef0100e6cae83b…  ← 同一个实现
（5 个全部委托到同一个实现合约）
FOMO evmAddress  0x000f527386…  (空，纯 EOA)
```

两个推论：

1. **所有交易账户委托到同一个实现合约**，`getCode` 的区分度是零；
2. EIP-7702 的委托由**账户自己的私钥**签名，授权人就是它自己。
   交易账户与 `evmAddress` 是**两个不同的私钥**，链上不存在把它们绑在一起的签名。
   而且该账户 ETH 余额为 0、nonce 为 1（只有那次授权），交易是被代付的，
   连资金流溯源都没有。

**结论：这个映射是 FOMO 后端的事实，不是链上的事实。**
「接一个链上 Transfer 溯源器就能把 candidate 升成 confirmed」这个说法**不成立**，
之前文档里那样写是错的。剩下的现实路径只有两条：

- **另找一个直接声明交易账户的接口**（`evidence_type='api_declared'` 就是为它留的）——
  目前没找到，`recipient` 已被上面的观测排除；
- **多币重复匹配的统计证据**：同一 `(userId, address)` 在 N 个**不同代币**上被独立
  金额匹配命中，碰撞概率随 N 迅速下降。这是**统计证据不是证明**，要不要认它可以升
  `confirmed` 是个口径决定。当前实现还做不了这个判断——`recordAmountCandidates` 的
  `ON CONFLICT DO UPDATE` 会**覆盖** `token_ca`，历史没留下（实测 1448 条候选全部
  只记得 1 个币），要做得先改成逐币观测记录。

在这两条之一落地之前，`fomo_wallet_links` 的 `confirmed` 保持 **0**，
卡片上的盈利榜交集继续写「已确认至少 N 人」。

## 4. 仍待确认

1. 原版截图的 Top10 到底是「全链地址前十」还是「FOMO 持币账户前十」——截图无法**证明**，
   但两个样本给出了倾向性证据：

   | 样本 | 复核时全链持币 | 复核时 Fomo 持币 | Fomo 占比 | 卡片「账户识别」|
   |---|---|---|---|---|
   | MEME | 491 | 336 | 68.4% | 10/10 |
   | HDR | 173 | 20 | 11.6% | **10/10** |

   HDR 这条是关键：只有 11.6% 的持币地址属于 FOMO 用户，若 Top10 取的是**全链地址**前十，
   要十个全部落在那 20 个 FOMO 用户里并不自然；而若取的是 `/hodlers/top` 返回的
   **FOMO 持币账户**前十，`10/10` 是**构造上必然**的结果。两条样本都恰好 10/10，
   与后者一致。

   这仍然只是倾向性证据——FOMO 发行的币，大户本来就可能都是 FOMO 用户。
   所以本项目采用「FOMO 持币账户前十」作为**暂定口径**，**不声称已完全复刻**。
